# Overlay layer execution record — rulings and deferred findings

From the Plan 2 execution ledger, which lived under the gitignored
`.superpowers/` workspace and would otherwise be lost at merge.

Plan: `docs/superpowers/plans/2026-09-02-flowreel-overlay-layer.md`

## Rulings

### Ruling R1: The plan's overlay host sets `contain: layout style size`. `contain: layout` establishes a containing block for `position: fixed` descendants, and every overlay element is `position: fixed`. They would resolve against the host rather than the viewport, which is coincidentally equivalent while the host is `inset: 0` but breaks the moment `document.documentElement` is transformed for zoom — precisely when the cursor must stay put. Decision: drop `contain` entirely from the host style. Carried into the Task 2 dispatch. Cost if wrong: losing a paint-isolation hint that was never needed; the host has no layout-affecting content.

### Ruling R2: Task 3's "passes through intermediate positions" test samples cursor position on a 15ms interval while an eased 400ms move runs. That is timing-sensitive by construction. Accepted rather than rewritten, because the property it checks — that movement is stepped rather than teleported — is the whole point of the task and there is no cheaper way to observe it. The assertion is deliberately weak (at least one sample strictly between the endpoints) so a slow machine still passes. Cost if wrong: a rare flake on a very loaded CI runner.

### Ruling R3: The Important finding (neither isolation test can detect a regression from `mode: 'closed'` to `mode: 'open'`) is plan-mandated — the test code came verbatim from my brief. I rule for the finding. The reviewer traced why both pass for the wrong reason: `resolveTarget` tries `getByRole('button')` first and matches the real native button before any text strategy runs, and `visibleButtonNames` uses plain `document.querySelectorAll`, which never pierces shadow DOM in either mode. So the only thing currently proving the closed-root guarantee is a code read. This is the same class of defect as the vacuous encoder test in Plan 1, and the guarantee is the entire reason the task exists. Fix dispatched. Cost if wrong: one extra assertion.

### Ruling R4: The reviewer measured a nominal 300ms cursor move taking 556-594ms wall-clock (~2x), because each step pays a page.evaluate round-trip on top of a fixed 16ms waitForTimeout. It graded this spec-level rather than a defect, correctly, since my brief's reference implementation causes it. I rule to fix it anyway: this tool's entire product is how the recording looks, and every glide running at half the requested speed reads as sluggish on playback. The fix is small — drive interpolation from elapsed wall-clock against a deadline rather than from a step index, so the animation takes the time it says. Cost if wrong: a move on a very slow machine renders fewer intermediate frames rather than running long, which is the better failure for a recording.

### Ruling R5: The ripple cleanup flake (1 failure in 18 runs; a .fr-ripple node still present 500ms after a 150ms animation) lives in src/overlay/browser.ts, which Task 4's brief placed off-limits, and the reviewer recommended tracking it as a follow-up rather than blocking this gate. I rule to fix it now instead, and to lift the browser.ts restriction for that one change. Reasons: it is a genuine intermittent CI failure, flaky tests corrode trust in the suite faster than almost anything else, the fix is two lines, and `Node.remove()` is documented as a no-op on an already-detached node so the belt-and-braces double removal is safe. Deferring a known two-line fix for a known flake is worse than the scope purity it would preserve. Cost if wrong: a redundant timer per ripple and chip, firing after the node is already gone.

### Ruling R6: CORRECTING MY OWN PRESCRIPTION. I specified the fallback margin as `ms + 400` without checking it against the test's wait window. With ms=150 that is 550ms against a 500ms wait — the fallback could never fire in time, and the implementer demonstrated this deterministically (2/6 failures with the primary path disabled) rather than silently adjusting the number. Corrected margin is `ms + 200` (350ms), comfortably inside the 500ms wait. Rejected the alternative of lengthening the test's wait, because that is exactly the "widen until green" move I forbade when raising the finding. Cost if wrong: a ripple delayed by more than 200ms past its own 150ms animation would be removed slightly early — visually harmless, since the animation ends at opacity 0 and any node still alive at that point is already invisible.

### Ruling R7: Adopting the reviewer's `vi.spyOn(Overlay, 'install')` proposal over my three suggested alternatives. `install` is a static method reached by property access, so the spy mutates the one shared class object both the test and run.ts reference, and default spyOn behaviour calls through — it is a wiretap, not a stub, so the overlay still genuinely installs and the rest of the assertion still exercises real behaviour. My alternatives were all worse: hashing two full runs fights frame-count nondeterminism and could pass for the wrong reason, file-size comparison is too fuzzy to assert on, and a testability seam adds production surface for a test. Cost if wrong: a spy that silently stops matching if the call site is ever refactored to a destructured import, which would show up as the test failing rather than passing.

### Ruling R8: R1's REASONING WAS WRONG, and the review proved it. I removed `contain: layout` from the overlay host believing that kept the cursor resolving against the viewport once zoom transforms the page. It does not. The host is appended to `document.documentElement` and `setZoom` transforms `document.documentElement`, so the host is a DESCENDANT of the transformed element — the transform establishes the containing block and paints the host inside the scaled subtree regardless of `contain`. Removing `contain` was harmless but bought nothing, and the defect I thought I had pre-empted is fully present: during a zoom the entire overlay is scaled and displaced, the cursor lands away from what it is clicking, and the host's `inset: 0` resolves against the document rather than the viewport so a caption can be off-screen entirely. Fixing by transforming `document.body` instead, leaving the host — a sibling of body — outside the transform. Cost if wrong: an app whose own fixed-position elements are positioned against the html element would shift during zoom; the app's own fixed elements shifting under zoom is already documented in the spec as acceptable.

### Ruling R9: Fixing all five Important findings plus the example rewrite in one wave, per the process's single-fix-wave rule. F4 (overlay state lost across navigation) is the largest at ~15 lines and I am including it rather than deferring: every multi-page app hits it, and the symptom — caption vanishing mid-recording and the cursor teleporting back to the corner — looks like a bug in the tool rather than a limitation. Cost if wrong: a navigation listener that re-applies stale state if a script deliberately wanted a clean slate after navigating.

### Ruling R10: Also folding in four Minors that are cheap and directly visible in output: distance-scaled glide duration (the reviewer called it the highest-leverage polish tweak left), chip duration scaled to typing time (currently the chip vanishes mid-type), skipping the press chip when the cursor has never moved (it draws clipped at 0,0), and a chip max-width (a long typed string currently renders wider than the viewport). Deferring the rest. Cost if wrong: a slightly larger fix wave than strictly required to merge.

### Ruling R11: The implementer found my proposed F1 test could not discriminate — I placed the cursor target at the zoom origin, and a scale transform does not displace its own origin point, so it would have passed against the broken code. It used non-coincident points (zoom origin (700,50), cursor (50,550)) and captured the actual displaced position (-343.2, 846.8) under the old code. It also found the 200ms settle wait I implied was itself racy and let the buggy code pass by accident, raising it to 800ms. Accepting both. Cost if wrong: none — this is strictly a stronger test than the one I specified.

### Ruling R12: Accepting the implementer's widening of CHIP_TAIL_MS from 300 to 500 after one flake under full-suite load. The re-review judged it legitimate tuning rather than "widen until green", because the constant is a jitter margin on a timing tail, not a correctness threshold. Noting the reviewer's caveat: the tail is flat rather than scaling with text length, so a very long typed string under heavy load could still flake by the same mechanism. Deferred. Cost if wrong: a rare flake on a long `type` line.

## Deferred findings, still open

- Task 4: note — the implementer flagged that a raw backtick inside OVERLAY_SOURCE's comments would break the outer template literal and silently kill the whole injected script. Worth carrying into any future edit of browser.ts.
- Task 5: minor (deferred): cursor-arrival logic (resolveTarget -> centreOf -> showCursor/moveTo) is duplicated across click/type/hover; a shared `arriveAt` helper would remove ~6 lines.
- Task 5: minor (deferred): `centreOf` calls boundingBox() even when no overlay is present, adding one CDP round-trip per click/type/hover on the no-overlay path. Zero behavioural difference; comes from my brief's reference code.
- Task 5: minor (deferred): zoom/highlight short-circuit before resolveTarget when no overlay exists, so a bad selector in those commands is silent without an overlay but throws with one. The reviewer judged this correct — it preserves the exact prior no-op behaviour — but it deserves an explanatory comment.
- CHIP_TAIL_MS is a flat 500ms tail rather than scaling with text length, so a very long `type` string under heavy load could still flake.
- Consecutive `zoom A` then `zoom B` at different origins still snaps; needs a translate+scale composite.
- A raw backtick inside `OVERLAY_SOURCE` silently kills the injected script and yields a successful, overlay-free recording. Worth a parse guard.
- Strict-CSP apps may drop the overlay's inline `<style>`, producing an unstyled but present overlay with no error.
